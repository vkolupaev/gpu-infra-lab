# waves-rr05: pre-registered question and hypothesis

- Written 2026-11-11 (draft), committed 2026-11-23, before the run. Planned run:
  2026-11-24 (session 1, part `n`, last), Vast A100-SXM4-80GB.
- Config: `configs/qwen3-8b-bf16-rr05.yaml`; run with `bench.py`.
- Baseline: [first-number](2026-10-25-first-number.md) - the same setup with fixed
  lengths, where the waves were seen.

## Question
In a closed loop at C = 8, does a ±50% spread of request lengths (`--random-range-ratio
0.5`) break up the synchronized waves seen with fixed lengths in our baseline run
(first-number), and how much does that change TTFT and the spread of E2E latency?

**Setup,** identical to first-number except the length spread: Qwen3-8B BF16, vLLM 0.32.0
(no tuning), 1x A100-SXM4-80GB (Vast), 1024 in / 256 out, C = 8, `--request-rate inf`,
`--ignore-eos`. Baseline (fixed lengths, first-number, C = 8): std@E2EL 7.9 ms, p50@TTFT
485 ms, p95@TTFT 538 ms; GPU power dips repeat every ~3.6 s.

## Hypothesis
**Mechanism.** With fixed lengths all 8 requests finish on the same decode step, so 8 new
requests arrive together and are prefilled as one ~8192-token chunk: every TTFT waits for
that chunk (~485 ms), and the loop runs in waves (one wave per ~3.6 s). With lengths
spread over [0.5·L, 1.5·L], completions are spread out, new requests arrive one or two at
a time and join the running batch, so each waits for a 512–3072-token prefill (inputs are
now 512–1536 tokens) instead of 8192.

**Expected:**
- std@E2EL grows from 7.9 ms to ~0.8–1 s, waves or not: output lengths are uniform over
  128–384 tokens (std ~74 tokens), and E2EL scales with output tokens × TPOT (~11–14 ms).
  A sanity check of the length spread, not a test of the waves.
- p50@TTFT drops from 485 ms to ~100–250 ms.
- The regular power dips every ~3.6 s blur out (observation in `gpu-monitor.csv`,
  `power.draw` at 1 s; not a pass/fail criterion).

**Falsified if:** p50@TTFT > 400 ms (prefill still arrives in large chunks: waves
persist).

**Pre-check:** checked in the lab image (vLLM 0.32.0): lengths are uniform in
[floor(L·(1−r)), ceil(L·(1+r))] (`vllm/benchmarks/datasets/utils.py`). On the host, before
the run: `vllm bench serve --help | grep -A3 range-ratio`. If the semantics differ, record
it in the experiment note before looking at the results (this file is not edited after its
commit).
