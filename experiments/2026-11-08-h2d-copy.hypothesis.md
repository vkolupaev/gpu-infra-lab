# h2d-copy: pre-registered question and hypothesis

- Date written: 2026-11-04 (before the run). Planned run: 2026-11-08, Vast A100-SXM4-80GB.
- Host: machine 142924 preferred (the first-number host); otherwise any A100-SXM4-80GB that passes
  the preflight. The host used is recorded in the note.
- Script: `pytorch/h2d_copy.py` (1 KiB .. 1 GiB in x4 steps; pinned / pageable; h2d / d2h).
- Inputs: hwcheck h2d_pinned 18.8 GB/s (machine 142924, 2026-10-25) and 19.8 GB/s (2026-10-22);
  PCIe Gen4 x16 = 16 GT/s x 16 lanes x 128/130 = 31.5 GB/s per direction, raw.

## Question
How does copy time between host and device depend on size and on pinned vs pageable host
memory, and where does the latency-bound regime end?

## Hypothesis
Model: t(n) = t0 + n / BW.
- Pinned: BW = 18.8 GB/s (hwcheck from the first-number run, machine 142924, 2026-10-25),
  t0 = 13 us, range 7-23 us (assumed, geometric middle of the range). Budget per stage: Python + PyTorch
  dispatch 2-10 us, driver call (cudaMemcpyAsync) 2-5 us, copy engine start + first read round trip
  1-2 us, completion mark ~1 us, synchronize wake-up 1-5 us with a spinning wait (cudaDeviceScheduleAuto,
  more cores than CUDA contexts). Floor: a 1-byte CPU copy_ on a home Core i5 takes 0.7 us.
  A sleeping wait would give 16-68 us.
- Gap to the link: hwcheck h2d_pinned 18.8 GB/s (1 GiB copy, t0 < 2% of it) is ~65% of the
  protocol limit ~28.8 GB/s = 31.5 GB/s raw x 256 / (256 + ~24 B per TLP), assuming MPS 256.
  Assumed cause, not established: H2D is a pull - the GPU copy engine sends read requests to host
  memory and the data comes back in completions - so bandwidth <= bytes in flight / read round trip,
  as a TCP window caps a long path (at 28.8 GB/s and an illustrative 1 us round trip that needs
  ~28 KiB in flight); read completions may also be split into 64-128 B chunks (~84% efficiency at 128 B).
- n_half = t0 x BW = 239 KiB (128-422 KiB for t0 = 7-23 us): below it more than half of the time is
  latency. The 256 KiB sweep point is the closest one; effective BW there ~9.7 GB/s (BW x n / (n + n_half)).
- Pageable: one more CPU memcpy into a pinned staging buffer before the DMA.
  BW_memcpy = 11.3 GB/s (assumed: the driver copies with one thread; single-thread copy of 1 GiB on a
  home Core i5 gave 12.5 GB/s; taken 0.9 of it for higher server memory latency and possible NUMA on
  the dual-socket EPYC 7513 host).
  In series (no overlap): 1/BW_pageable = 1/BW_pinned + 1/BW_memcpy -> BW_pageable = 7.0 GB/s (pessimistic).
  Pipelined chunks (memcpy of chunk k+1 overlaps DMA of chunk k): BW_pageable = min(BW_pinned, BW_memcpy)
  = 11.3 GB/s (optimistic). Expected: 7.0 - 11.3 GB/s at 1 GiB; where it lands shows what the driver does.
- d2h vs h2d: d2h > h2d, up to the ~28.8 GB/s protocol limit. D2H is a push: the copy engine sends
  posted writes (header + data, no completion per transaction), so the read round trip that caps h2d
  does not apply; only receiver flow-control credits and the link remain. If d2h <= h2d, the host side
  (root complex, IOMMU, memory, NUMA placement of the buffer) throttles inbound writes.
  Pageable d2h uses the same staging in reverse (DMA into staging, then CPU memcpy out): same 7.0 - 11.3 GB/s corridor.

Falsified if: the pinned 1 GiB copy differs by > 5% from hwcheck h2d_pinned measured on the same host
in the same session (`results/2026-11-08-session/hwcheck.json`; both are 1 GiB pinned copies, the
methods differ by < 1% at this size); pageable is not slower than pinned at 1 GiB; n_half is outside
50 KiB - 2 MiB.

## Expectations recorded earlier, before any measurement (not revised)

Source: lesson 1.1, section 4.3 item 5, 2026-10-31, written after reading
https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html

1. non_blocking=True speeds up H2D transfer for pinned memory by ~4.5%.
2. non_blocking=True speeds up H2D transfer for pageable memory by ~19.35%.
3. The expectation was written after reading the tutorial.

Not tested in the 2026-11-08 run: `h2d_copy.py` keeps `non_blocking=True` with a synchronize after
every copy, so blocking vs non_blocking is not swept. Deferred to a later run.

Conditions of the tutorial benchmark (added 2026-11-04, read from the tutorial page):
- "Synergies" subsection: 1000 tensors of 1,000,000 float32 elements each (`torch.randn`), copied in a Python loop with `.to("cuda:0")`.
- Timings (median of `torch.utils.benchmark.Timer.adaptive_autorange(min_run_time=1.0, max_run_time=20.0)`):
  pageable blocking 378.8198 ms, pageable non_blocking 305.4993 ms; pinned blocking 313.5409 ms, pinned non_blocking 299.4534 ms.
- Non_blocking variants call `torch.cuda.synchronize()` once after all 1000 copies. Copy only; the GPU model is not stated on the page.
- The percentages are derived from these timings: (378.8198 - 305.4993) / 378.8198 = 19.35%; (313.5409 - 299.4534) / 313.5409 = 4.5%.
